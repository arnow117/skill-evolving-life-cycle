## Implemented behavior

- `build_codex_policy_template` now defaults to schema 3. Schema 1 and schema
  2 retain separate normalizers, profiles, preparation semantics, bindings,
  native-fragment checks, and argv rendering.
- A schema-3 template fixes one routing parameter and renderer. After install,
  the evaluator reconstructs the frozen explicit `@skill + JSON` request,
  verifies its DTO against one declared `python-script-v1` action, confirms the
  selected registered Codex entry, and calls the existing
  `_discovery_read_binding` helper for the installer link, entry, and protected
  `/bin/cat` reader identities.
- The private policy binding records the selected skill/action, exact routing
  command and path, installation version/composite, entry identity, reader
  identity, rendered guidance digest, and pathless guidance summary. Rebuilds
  before launch and during collection must reproduce that full binding.
- The schema-3 CLI argument vector receives the exact rendered developer
  instruction. Native collection requires exactly one matching-turn
  `generic.developer_instructions` item with that same rendered literal.
  Public reconstruction returns only the digest and pathless summary.
- Invalid selection, an unrelated input path, a replacement directory or
  registration, entry drift, a non-literal command, a changed launch binding,
  and a changed native fragment fail closed before qualification.
- README, author guidance, and generated `MAINTENANCE.md` describe schema 3 as
  untagged experimental source behavior. They state that schemas 1 and 2 stay
  compatible and that v0.2.0 assets do not include this feature.
