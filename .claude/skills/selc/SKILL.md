# SELC suite lifecycle

Resolve this skill's repository root before running commands; the chat may be open in a different directory. Use that repository's runtime at `scripts/selc.py`. Read its root `README.md` for the current command syntax, scenario IDs, parameters, and verified local journey.

SELC v0.2.0 supports a BASIC source and portable distribution path: create, validate, seal, package, ordinary installation, explicit upgrades, standard-library execution, and the offline `stats-report` HTML command. This authoring meta skill is for Codex only. A WorkBuddy user consumes an ordinary skill ZIP or a generated suite; it does not use this authoring skill. BASIC use creates no hooks, needs no native receipt, and produces no automatic statistics. The observed automation path is **EXPERIMENTAL**: observed hooks, native attribution, one-shot results, real creator/evaluation, and automated contribution or release require their own evidence. It can currently stop with `RECEIPT_UNAVAILABLE`; it does not guarantee desktop behavior or support for a new host or model. A framework source release or ordinary example never qualifies a managed business candidate.

Create and maintain a suite as a single versioned unit. Each declared skill keeps its own entry directory. For an arbitrary managed skill, pass `create --managed-declaration <protocol-1-json>` with a `managed` protocol-1 section containing `actions` and `native_hosts`, plus optional top-level `artifact_checks` and `skill_artifact_checks`. The binding maps each declared skill to a normal manifest checker declaration; do not hide checker metadata under `managed`. Use `instruction-staging-v1` or put a generated `python-script-v1` script under `resources/`; do not ask users to record task, call, or delivery data. The generated suite contains its runtime, installer, maintenance guide, both Codex and WorkBuddy registration targets, and `runtime/SELC-LICENSE`; do not add an absolute local skill path to generated files.

When creating or substantially editing a skill body, use the available `skill-creator` initializer and validator in the active Codex environment. Its optional PyYAML dependency belongs only to that creator environment. The portable suite runtime must remain Python standard-library only.

For a newly created authoring source, use this sequence: `create`, let skill-creator create or update the declared `SKILL.md` body and resources, run its validator, then run `seal --suite <authoring-source>`, `validate`, and `package`. `seal` explicitly refreshes only the source suite's content hash after checking its portable files and existing framework runtime hash. It does not execute business code, install the suite, or treat an installed local edit as a clean baseline. Installed-suite changes continue through an isolated `evolve` candidate.

Start normal installation in `basic` mode: `install` and generated `install.py` default to it, or users can write `--mode basic` explicitly. Basic registration points directly to an ordinary `basic_path` body (or the normal `path` for a non-managed skill), creates no hooks, requires no native receipt, and does not create automatic success statistics or evaluation eligibility. A fresh basic WorkBuddy installation must work when `.codebuddy/settings.json` is absent or unrelated malformed JSON; never repair or overwrite that file for ordinary use. The installation result reports the selected mode and disabled observation status. Existing installations preserve their saved mode when the argument is omitted; legacy registrations lacking it are observed for compatibility, and updates/recovery keep the selected mode.

Use `--mode observed` only for the **EXPERIMENTAL** automatic native-receipt, managed-execution, publication, and strict-evidence path. It retains the installer-owned managed entry and collector hooks. An observed-only legacy body with no `basic_path` must fail basic preflight with `BASIC_ENTRY_UNAVAILABLE`; do not rewrite its business instructions. A mode switch is suite-wide across registered Codex and WorkBuddy harnesses, removes only documented suite-owned hook commands when switching to basic, and waits for active task, call, session, or managed execution leases. Artifact checks establish business results separately from native observation: a complete host interval is also required for one-shot success, and a fixture cannot establish production completeness. Missing or ambiguous evidence remains `unknown`. Never store artifact text or feedback text in an exported snapshot.

For an owner-facing local snapshot, run `stats-report --project-root <project> [--project-root <project> ...] --output <report.html> [--include-test]`. The v0.2.0 source archive and a complete generated suite expose this command through their respective local CLI wrappers; a runtime-only framework ZIP does not. The standalone HTML works by double-clicking and refreshes only when regenerated. It reads supported rollback-journal protocol-6 records stores without initializing, exporting, migrating, or mutating them. Keep selected projects separate, show only count metrics and declared grouping dimensions, and never embed source paths, identifiers, evidence, prompts, logs, or credentials. A `basic`-only registry can be an empty source, not a health claim; unreadable sources are partial errors when another source is usable, while all-source failure preserves an existing output.

`evolve evaluate` is an **EXPERIMENTAL** fixture diagnostic and never authorizes a contribution or release. For a real Codex evaluation, first run `evolve policy-template --host-version <observed-alpha11-version> --python-read-root <narrow-python-root> --output <private-template.json>`, then copy the complete generated object to the Codex matrix's `tools_policy_template` before `evolve plan`. The template freezes approval, network, tools, fixed CLI profile, all read/write roots, the OS-derived account home, and version-2 normal project-and-five-hook trust inheritance. Only the canonical isolated project and the observed account-bound alpha.11 `arg0` bootstrap path can vary; a raw `tools_policy_digest` plan remains unverified. An isolated attempt must already be below one existing non-symlink direct Git root: SELC finds that root read-only and rejects a worktree `.git` file, nested root, or mismatched Git identity. Before launch, trust that exact enclosing root and exactly its five installed definitions through Codex's normal UI. SELC retains `--ignore-user-config` and passes only the original trusted actual-root `projects` key/value plus the five matching `hooks.state` hashes in quoted public inline-table `-c` values; missing, untrusted, aliased, changed, wrong-source, disabled, extra, or relevant more-specific-untrusted entries are refused. Run `evolve creator prepare --binary <codex> --binary-version <version> --brief <maintainer-regression.txt> --skill-creator-root <trusted-skill-creator-root> --creator-python-root <trusted-python-runtime-root>`, retain its original native Codex JSONL session and verify it with `--native-evidence`, then `evolve bind --variant <candidate-variant>`, one isolated `evolve attempt` per required unit, `evolve attempt native-evidence-template`, and `evolve finalize` with every binding being reported. The brief is explicit regression/goal text only: never include holdout, oracle, protected paths, or their contents. The fixed profile binds the brief hash and prompt, ignores user configuration, allows writes only to candidate skills/resources, and permits reads only for the selected `skill-creator` root (including `scripts/quick_validate.py`) and Python runtime root. Creator evidence must show the matching session metadata, user turn, `exec` tool, effective no-network policy, exact readonly roots, candidate-only writes, and explicit protected-path denies; a profile JSON or file mode alone is insufficient. Attempt collection re-reads the original host-store cutoff SHA-256, path hash, device, inode, and native policy. It requires duplicated filesystem entries in `permission_profile` and `file_system_sandbox_policy` to agree exactly, records the raw policy hash and validated parameter mapping, and rejects an additional permission or another account/bootstrap shape. Codex outer `exec` IDs and hook tool IDs are separate namespaces. A baseline binding generated by the plan can retain observed initial-version evidence; a candidate pass never authorizes another snapshot or scope.
